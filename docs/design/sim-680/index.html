#680 · A deterministic simulation of drive, fast, check, merge and kick

Design for the owner to approve. Branch issue-680 · 2026-11-08 · design lane drover-design-680

The real pass code runs as a set of "processes" (one OS thread each). A seeded scheduler lets only one of them run at a time. Every call a pass makes to herdr, gh, git, ps or kill already goes through Runner. That call is the yield point: an in-process model answers it, the fake clock moves on, and the seed picks which process runs next. Invariants are checked after every step. Production code gains two small seams, a clock and a yield hook, about 30 src/ lines. The fix for the incident adds about 25 more.

1 · The first seed: drover-rev-370-r5, 26 supersedes in "one second"

From state.db, issue drover#370: every supersede, spawn and kick between seq 21420 and 22260 carries the same ts, 1793805085 (2026-11-04 22:11:25). That is 26 supersede, 28 spawn and 30 kick events. The lane's own later lane-closed key says it actually spawned at 1793805278, about 3 minutes later. So it was not one second. It was one frozen clock across a run of minutes.

Mechanism to confirm in the sim

drive::kicked runs up to 30 drive passes under one Ctx, and ctx.now is set once at process (or service job) start. Each pass that sees the rev lane's verdict file but no verdict event re-spawns review with --supersede. That spawn's push or prompt re-flags kick-…​.again. All the time-based guards (#666 "superseded once", the stall threshold, spawn_pending_max_secs) compare against a clock that never moves. So nothing stops it until the 30 iterations run out.

This is a hypothesis, read from the log. Seed 1 must reproduce it on current staging before any fix lands (AC 2).

2 · Invariants: the final list

All of them are checked after every step, unless a row says "at quiet points". A quiet point is a moment when no pass is inside a spawn, between its pane create and its spawn event. The checker reads the model's ground truth (panes, PRs, true time) and the real state.db event log. It never reads drover's own view.

3 · Scheduler and the production seams

Processes as baton-passing threads

  • Each pass is one OS thread running the real entry: drover_core::main_with(["drover","drive",…], &ctx, &sim, …), and likewise drive --fast, check, merge, kick --now and the owner and conductor verbs. Thread-locals (IN_ACT, KICK, SLOT, ROOM, the db connection cache) are per thread, which matches per-process state.
  • One baton, a Mutex plus Condvar. A thread runs only while it holds the baton. At each yield point it hands the baton back, and the scheduler picks the next runnable process with a SplitMix64 PRNG seeded from DROVER_SIM_SEED, written in about 15 lines of test code (no rand).
  • Discrete-event clock: each modelled call costs virtual seconds (herdr agent start 3 s, gh 1 s, git 0.5 s). r.sleep(n) parks the process until now + n. When nothing is runnable, the clock jumps to the next wake-up or scenario event.
  • Timers start passes as launchd does: drive every 300 s, fast every 60 s, check every 300 s, each with seeded jitter, so passes of the same kind overlap. Runner::detach on kick --now starts a new process with a model pid.
  • A panic in a process is a failure, with the seed and the trace.

Seams added to production ≈30 lines

Clockcrate::now() reads a thread-local override first, which the sim sets. The two direct uses (drive.rs:231, :663) and the service's drover_core::now() already go through it. Ctx.now stays the per-process start time, the real behaviour the sim must expose. ~8 lines. Yield hookcrate::sim::point(&Point): a thread-local Option<&dyn Fn>, a no-op unless set. Called in db::append (with the event), db::take, db::release and db::claim, so read-modify-write races on state.db interleave too, not only those between external calls. ~15 lines. RunnerNothing new: the sim's Runner is the yield point for herdr, gh, git, ps, kill and detach. local() is false, so herdr::STREAMED stays unused. DeterminismAny HashMap iteration that reaches a Runner call or an event becomes a BTreeMap. The determinism test finds these. Budget ~5 lines.

The real state.db (rusqlite) runs in a temp dir per seed, along with real worktree folders and verdict.md files there. No network and no child process: every Command goes through the sim Runner.

4 · The fakes' surface

A single stateful Model (test code, crates/cli/tests/sim/model.rs) answers the argv that drover builds. Each argv is parsed by its leading words. An argv the model does not know fails the run with "unmodelled call", so new production calls cannot silently get a canned answer.

5 · The scenario generator

From the seed

  • 1–2 fleets, 2–6 issues, 1–2 hosts. review_rounds, max_parallel_spawns and serial groups are drawn from small ranges.
  • Queue verbs over time: add (some --serial, --design, --repro), block, unblock and mv, issued as owner processes.
  • Per lane, a script drawn from: finish clean · push and then turn done · write the verdict late · die mid-turn · never confirm the prompt · get capped · hang (stall).
  • Per head: CI goes pending → green or red after 1–15 sim minutes. Verdicts are PASS or FAIL, with or without proof.
  • Host events: going offline and back, load spikes, low disk. Integration moves when other PRs merge, which makes update rounds.
  • Crashes: a running pass is killed at a random yield point, so its leases and half-done spawn are left behind.

Run, trace and replay

  • One run is 6 sim hours or 4,000 steps, whichever comes first, then a 30 sim-minute settle with no new faults for the liveness check (I6).
  • The trace is one line per step: step · t · process · call or event · model reply (short). It is kept in a ring buffer, and the last 200 lines plus every scenario event are printed on failure.
  • DROVER_SIM_SEED=<n> cargo test -p drover --test sim replays one seed. DROVER_SIM_TRACE=full prints all of it.
  • Determinism test: seed 7 is run twice in one process, and the two traces must be byte-equal.
  • Fixed set: crates/cli/tests/sim/seeds.rs lists seed 1 (the #370 incident), seeds 2–24 and every later regression seed, with a one-line note each. The target is under 60 s on CI.
  • just sim [N=500] runs N random seeds and prints any failing seed. A nightly CI job runs just sim 2000. A failing seed goes into the fixed set with its fix.

7 · Open questions for the owner

  1. Fix scope. AC 2 asks for the fix that makes seed 1 pass. Recommendation: fix what seed 1 needs here and file the rest.
  2. I7's 60 s tolerance. A long pass legitimately writes events stamped with its start time. Is 60 s the right bound, or should events take the true time and Ctx.now stay only the pass's decision time? The second changes what ts means and touches more code. Recommendation: 60 s, and the fix refreshes now per kick iteration.
  3. Nightly job. It is a new scheduled GitHub Actions workflow (CI minutes, about 10 min a night). Is that OK, or should it be just sim by hand only?
