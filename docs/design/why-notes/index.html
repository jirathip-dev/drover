Why notes: each lane commit linked to its reasoning

Design for drover#677 · branch issue-677 · design lane, 2026-11-08

git notes refs/notes/whyno new dependencyno old-board UI filesrc/ estimate +215 (issue guess +150)

A lane writes a short why.md. On drover turn done drover checks it and attaches it to the pushed head as a git note. The note is also copied into the PR body and logged as a why event. Briefs, reviewers and drover why <file:line> read it back. Only drover writes notes, and it writes them from the main host's clone, never from a lane.

1 · The note form

why.md  (worktree root, never committed)
Decided: per-file 5 MB and per-snapshot 50 MB caps; a skipped file is listed in the wip commit
Because: "A per-file cap (default 5 MB) and a per-snapshot cap (default 50 MB) skip larger files."
Decided: build dirs are excluded by pathspec, not by .gitignore
Because: "whatever a repo's `.gitignore` says"
Rejected: reading .gitignore only — other fleet repos ignore only target/
Rejected: splitting wip prune into a follow-up — the owner chose a cap raise
Because: q799
Check: kill with a 60 MB file under target-lane/ names it skipped
Owner: wip saves stop carrying build output; huge files are listed, not pushed
keycountwhat
Decided:≥ 1One choice the diff makes.
Because:≥ 1Its reason. Must carry a citation (below). It covers the Decided:/Rejected: line above it.
Rejected:≥ 1alternative — why (an em dash or --). Rejected: none — … is allowed.
Check:≥ 1What the reviewer should verify.
Owner:exactly 1, last lineOne plain-words line. This is the line the merge comment and /api/v1 show.

Lines may repeat in any order, except that Owner: comes last. Blank lines are ignored. At most 15 non-blank lines, each at most 240 chars, 2 KB in total. No other line prefixes, so no prose and no headings.

Citations on Because: (every one is checked, not only shaped)

formaccepted when
"quoted text"The quote appears verbatim in the issue spec cached at spawn plus its ## Amendments, comparing with whitespace collapsed and backticks kept. At least 12 chars.
q<id>The id is an ask on this fleet that is answered (a decision event, owner or by: default).
path:lineThe path is in the head commit's tree and the line is within its length. .drover/rules.md:7 works too.

A line can carry more than one citation. One valid citation is enough.

2 · Writing: turn done → note on origin

  1. Lane side. drover turn done reads why.md and runs the form and secret checks right away. These are pure checks, so a remote lane gets the refusal before its line goes to the outbox (#389).
  2. Main host (local lanes directly; remote lanes when drive delivers the outbox). This applies only when the turn is done and the PR head is a new push, using the condition TURN_NUDGE already uses. Otherwise nothing note-related happens. drover reads why.md through the lane's host (hosts::On, so ssh for a remote lane) and runs the full check, citations included.
  3. Invalid: turn-end is still logged, with "note":"WHY_INVALID: …", and the turn exits 3. Drive answers with WHY_NUDGE: one prompt that quotes the reason, sent before the review starts. After that one nudge, the next turn done goes to review even with no note. The rev brief then says no why note: <reason>, so a doc never blocks the pipeline (open question 1).
  4. Valid: drover takes the lease why-notes:<fleet> (the leases table, 120 s) and works in the fleet's local clone (repo.local): 
    git fetch origin <branch> +refs/notes/why:refs/notes/why-origin   # head object + origin's notes (ref may not exist yet)
git notes --ref why merge -s theirs refs/notes/why-origin          # skipped when why-origin is absent
git notes --ref why add -f -F <tmp> <head>
git push origin refs/notes/why:refs/notes/why                      # never --force
    A non-fast-forward reject loops back to the fetch, up to 3 times. The lease serialises drover's own processes. The fetch, merge and retry cover any other writer. If all 3 tries fail, drover logs why-failed with the git error, the review is not blocked, and the next drive pass retries from the kept copy.
  5. PR body: gh pr view --json body. The section ## Why (round n) is replaced if present (up to the next ## ), else appended. Then gh pr edit --body. n = the review round this head enters (rounds + 1). A second push in the same round replaces that round's section, and the older head keeps its own note.
  6. Event why: {sha, round, branch, agent, owner, files}. files lists the paths changed since the previous noted head (else since the base). owner is the Owner: line, so /api/v1 and the merge comment never read git.
  7. Consume: why.md is moved to .drover/why-r<n>.md in the worktree. A fix round has to write a fresh one, and a stale note can never be re-attached. why.md joins OWN_FILES, so wip snapshots and clean treat it as scratch.
Only drover writes notes. The hook gains one guard for every lane: git notes writes (add|append|edit|copy|merge|remove on any ref) and any git push naming refs/notes → REFUSED NOTES_DROVER_ONLY. Reading (git notes show, git log --notes=why, git fetch … refs/notes/why) stays allowed.

Survival through merge

Merges already use gh pr merge --merge (gate.rs, unchanged), so the branch commits and the notes on them reach staging. Notes live in refs/notes/why on origin, apart from any branch, so deleting a branch, running wip prune or a --update merge never drops them. Plain git reads them:

git fetch origin refs/notes/why:refs/notes/why && git log --notes=why

3 · Reading: drover why <file:line> [--json]

  1. Fetch notes quietly into the repo that holds the cwd (any worktree, or repo.local with --fleet). A fetch failure is ignored.
  2. git blame --porcelain -L n,n -- file gives the commit S.
  3. Issue: the first-parent merge that brought S into the integration branch (git log --merges --first-parent --ancestry-path S..<integration>, last one), then the merged event with that merge_sha. Fallback: the (#N) in S's subject. When the line is still on an open branch, the branch name issue-N gives the issue.
  4. Note: S's own note, else the issue's earliest why event whose head S is an ancestor of. That is the round that pushed S, since notes sit on round heads and blame usually lands on an earlier branch commit.
  5. Asks: the issue's needs-decision events with their decision (choice, by, via), plus every q<id> the note cites.
The sample below uses real data: blame, sha, PR, merge and the q799 ask and answer come from the live repo and event log. #646 predates notes, so its note text is illustrative, written the way the #646 impl lane would have written it.

7 · Open questions for the owner

  1. After the one nudge. If the lane still has no valid note, should review go ahead without it (recommended: the rev brief names the gap and the reviewer may FAIL it), or should the issue block until a note lands?
  2. Note per head or per commit. The spec says head, and this design keeps that. why maps an earlier branch commit to its round's head. The alternative is noting every commit of the push: blame lands directly on a note, at the cost of more notes and the same text repeated.
  3. Quote check strictness. A "spec quote" must appear verbatim in the cached spec plus amendments. Is that right, or should a shape check be enough?
  4. The update round's note. An --update head is often a pure merge from staging. Should it need a full note, or would a one-line Decided: merged staging; Because: q<id>|file:line … be allowed (the form stays the same, only shorter)?
